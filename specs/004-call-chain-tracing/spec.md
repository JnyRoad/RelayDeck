# Feature Specification: 完整模型调用链追踪

**Feature Branch**: `004-call-chain-tracing`
**Created**: 2026-09-03
**Status**: Draft
**Input**: 为 RelayDeck 的每次模型调用提供可在配置留存期内调阅的完整链路：调用人和 API Key 归属、客户端请求与 prompt、每次上游尝试的实际载荷和结果、最终客户端响应，以及按同一可靠会话连续回放的聊天式详情和原始取证视图。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 按调用人或 Key 定位调用 (Priority: P1)

管理员需要按调用人、已使用的 API Key、请求标识、模型和结果定位一条模型调用，不需要下载或浏览正文就能判断归属、路由和执行结果。

**Why this priority**: 没有可检索的归属索引，管理员无法从大量调用中找到需要分析的记录。

**Independent Test**: 创建不同用户和 Key 的调用后，管理员可以按其中任一身份筛选，看到正确的调用摘要而不接收任何请求或响应正文。

**Acceptance Scenarios**:

1. **Given** 已记录多位用户及多个 Key 的调用，**When** 管理员按用户或 Key 搜索，**Then** 仅返回匹配调用的时间、归属、模型、账户、结果、耗时与链路标识。
2. **Given** 调用归属的用户或 Key 之后被重命名或删除，**When** 管理员查看仍在留存期内的链路，**Then** 仍能看到该次调用时的非敏感归属快照。

---

### User Story 2 - 以聊天界面回放同一会话 (Priority: P1)

管理员需要从列表打开一条调用后，进入独立、可滚动的聊天式详情。详情按时间顺序展示该可靠会话中此前和后续的每轮用户提交及模型最终回复，并明确当前从列表打开的是哪一轮。

**Why this priority**: 逐条 JSON 或表格内容无法让管理员理解上下文；将一轮放回连续对话，才能有效追溯 prompt、回复和后续行为。

**Independent Test**: 对一个有至少三轮记录的同一会话，管理员从中间一轮打开详情后，可在单一可滚动窗口中阅读所有三轮的用户输入和模型回复，且中间一轮被定位和标识。

**Acceptance Scenarios**:

1. **Given** 同一可靠会话已有多轮文本调用，**When** 管理员从其中任一记录打开详情，**Then** 首屏是类似普通 AI 聊天窗口的按轮对话，用户提交和模型最终回复完整可读、可上下滚动，并自动定位到当前记录。
2. **Given** 某轮包含流式、失败或部分完成结果，**When** 管理员查看会话回放，**Then** 对话中展示实际已交付内容及明确的失败或未完成状态，不把该轮伪装为完整回复。
3. **Given** 调用缺少可靠会话标识或明确的续接关系，**When** 管理员打开详情，**Then** 仅显示该调用本身，明确标为“未关联会话”，不得按用户、Key 或相近时间推测合并其他调用。

---

### User Story 3 - 查看一条完整调用链和原始内容 (Priority: P1)

管理员需要在聊天式回放之外，切换到原始链路取证视图，按实际时间顺序查看客户端请求、路由、每次上游尝试、上游结果和最终客户端响应，以复现、分析或导出证据。

**Why this priority**: 聊天回放服务于理解上下文，但无法解释模型映射、上游改写、失败或重试；原始链路是可验证的分析证据。

**Independent Test**: 对一条至少包含一次上游调用的请求，管理员可从聊天回放切换至原始链路，查看完整步骤树并逐项调阅每个文本请求或响应正文。

**Acceptance Scenarios**:

1. **Given** 一条成功的非流式调用，**When** 管理员切换到“原始链路”，**Then** 能依次查看客户端请求、最终路由、上游请求、上游响应和最终客户端响应。
2. **Given** 一条发生两次上游尝试后成功的调用，**When** 管理员打开原始链路，**Then** 每次尝试均有独立序号、模型、账户、时序、状态及其对应请求和响应或错误内容。
3. **Given** 一条流式调用，**When** 管理员打开原始链路，**Then** 最终客户端响应展示实际交付的完整事件流，并明确该链路是否部分完成。

---

### User Story 4 - 以可控制的周期保留完整内容 (Priority: P2)

管理员需要自行填写调用链内容的保留天数，让完整 prompt 和响应在足够长的排障窗口内可用，同时自动清理到期内容而不让数据库无限增长。

**Why this priority**: 长期永久留存会让大体积模型内容不可控地占用数据库；没有完整正文又无法完成事后分析。

**Independent Test**: 管理员设置有效的自定义保留天数后，已到期链路及正文会被自动清理，未到期链路可完整调阅。

**Acceptance Scenarios**:

1. **Given** 管理员填写有效的正整数保留天数并开启自动清理，**When** 系统执行清理，**Then** 仅删除到期链路与其所有正文，保留未到期内容和独立的用量记录。
2. **Given** 管理员输入零、负数、非整数或超出产品允许范围的留存天数，**When** 保存设置，**Then** 系统拒绝该设置并明确指出输入问题。
3. **Given** 自动清理关闭，**When** 管理员预览或确认手动清理，**Then** 系统展示受影响的调用数、正文数和存储量后才删除。

### Edge Cases

- 上游在写出完整响应前失败、取消或超时：链路必须保留已发生的步骤和失败位置，不得伪装为成功。
- 上游重试、模型回退或账户切换：每次实际尝试必须按发生顺序保留，不能被最后一次结果覆盖。
- 客户端连接在流式响应中断开：已交付的内容与未完成状态必须一起保存。
- 调用没有客户端会话标识且没有协议声明的续接关系：只作为独立调用显示，绝不能用用户、Key、IP 或时间窗口将其拼接为会话。
- 输入或输出为非文本大媒体：必须保留链路元数据、大小与完整性信息；不把无法安全调阅的二进制内容伪装为完整 prompt 或文本回复。
- 追踪存储故障：模型网关的原有结果不受影响；该调用的链路状态必须明确说明哪些步骤未保存。
- 请求或上游响应携带认证材料：API Key、Authorization、Cookie、OAuth Token 和密码绝不能成为可调阅正文；这不改变正常 prompt 与模型输出的原文留存。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须为每次模型网关调用创建唯一链路标识，并关联请求标识、调用用户、API Key、调用组、选定账户、入口路由、模型和时序。
- **FR-002**: 系统必须保存调用归属的非敏感快照，使后续用户或 Key 的名称变化、禁用或删除不会使历史链路不可读。
- **FR-003**: 系统必须记录客户端发来的完整文本请求及 prompt，并保存最终实际交付给客户端的完整文本响应或事件流。
- **FR-004**: 系统必须为每次实际向上游发起的尝试保存独立、按顺序的步骤，包括路由后的模型与账户、上游请求、上游响应或错误结果、状态与耗时。
- **FR-005**: 系统必须只在明确的客户端稳定会话标识或协议明确的续接关系存在时，将多个调用关联到同一会话；不得以用户、API Key、IP、模型或时间相近性推断会话关系。
- **FR-006**: 打开某条调用时，系统必须在不挤占列表下方空间的独立详情视图中默认展示聊天式会话回放：按轮显示完整用户提交和最终模型回复、可上下滚动、定位当前调用，并固定展示会话和当前调用的关键元数据。
- **FR-007**: 详情必须提供清晰标记的“原始链路”视图，按发生顺序显示客户端、路由与每次上游尝试的原始请求/响应或错误内容；管理员可在聊天回放与原始链路间切换。
- **FR-008**: 系统必须支持按时间、用户、API Key、请求标识、链路标识、会话标识、路由、请求模型、上游模型、账户、结果和留存状态检索调用摘要；正文不得直接出现在列表接口或表格中。
- **FR-009**: 系统必须在每个文本正文上显示原始大小、保存大小、内容完整性状态和内容哈希，使管理员能区分完整、部分、不可用和非文本内容。
- **FR-010**: 系统必须完整保存正常的 prompt 与模型输出，不对其进行语义改写；认证凭据和会话秘密除外，必须始终排除在可调阅内容之外。
- **FR-011**: 系统必须让管理员填写有效的有限保留天数、启用或停用自动清理，并预览及确认手动清理影响；不得提供永久保留选项。
- **FR-012**: 自动和手动清理必须级联删除到期链路的所有步骤与正文，不得删除用量记录、账户、用户、API Key 或其他审计数据。
- **FR-013**: 只有已认证管理员可以读取完整链路与正文；链路读取、正文读取、复制和清理必须留下不含正文的操作审计。
- **FR-014**: 任何采集、持久化、查询或清理故障不得改变模型网关对客户端的响应语义；失败必须在链路元数据中可见。

### Key Entities

- **调用链**: 一次从客户端输入到最终结果的可检索模型调用根记录。
- **会话**: 由客户端明确提供的稳定会话标识或协议续接关系连接的一组调用；没有可靠关联依据的调用不属于会话。
- **链路步骤**: 调用链中按时间排序的一次客户端输入、路由决策、上游尝试、上游结果或客户端输出。
- **正文快照**: 某个链路步骤的完整文本输入、输出或错误内容，包含内容大小、哈希和可读状态。
- **调用归属快照**: 调用发生时的用户和 API Key 非敏感标识，用于历史检索和展示。
- **留存策略**: 管理员配置的有限保留天数及自动、手动清理状态。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员可通过用户、Key 或请求标识在一次筛选中定位目标调用，列表结果不包含正文。
- **SC-002**: 对带可靠会话关联的覆盖文本调用，管理员从任意一轮进入详情后可在一个可滚动的聊天式视图中阅读该会话全部已留存轮次，并定位当前轮；无可靠关联的调用不会被错误合并。
- **SC-003**: 对覆盖的成功、失败、流式中断及至少一次重试场景，100% 的实际已发生上游尝试都在原始链路视图中按顺序显示。
- **SC-004**: 对覆盖的文本调用，管理员能从原始链路读取客户端 prompt、每次上游请求/响应和最终客户端响应，并能区分完整、部分与不可用内容。
- **SC-005**: 任何待删除数据在清理预览中可量化；清理完成后，到期链路的步骤和正文均不能再被查询，未到期链路和用量记录保持可用。
- **SC-006**: 列表页保持只加载摘要；打开一条详情前不会请求该链路任何正文。

## Assumptions

- 本功能扩展现有模型调用追踪，不修改既有客户端模型 API 的请求或响应契约。
- 正文保存面向文本请求和响应；二进制媒体仍以元数据形式追踪，避免把数据库作为媒体仓库。
- 自定义保留期为管理员填写的正整数天数，产品允许范围默认设为 1 至 365 天；该上限可在后续根据容量证据调整，但永久留存不在范围内。
- 正文只由管理员按需打开；列表和常规分析接口不进行正文全文检索。
- 会话回放优先使用现有客户端协议传入的稳定会话标识；如协议提供明确的前序响应关系，也可作为续接依据。调用人或 Key 仅用于筛选和归属，不是会话边界。
- API Key 的身份、名称、掩码和不可逆指纹可用于追溯；明文 Key、认证头与令牌不属于可保存内容。
